4. WHY THE GATE REFUSES
-----------------------

Three observed causes. None of them is a property of this project's request, and
none can be fixed from the caller's side.

(a) The work-type classifier scores any prompt containing the word "review" as a
    review task and assigns it a context demand of 100,000 tokens. The reviewer
    prompt is roughly 1,200 tokens. The demand is a heuristic about the *kind* of
    work, not a measurement of the request, and a governance reviewer's prompt
    trips it by construction — the role is called reviewer.

(b) The model catalog carries no context window for the plain-inference provider,
    and cannot come to carry one. The catalog refresh copies a fixed list of
    metadata fields out of the provider's models endpoint, and context_length is
    not among them. Refreshing the catalog therefore never populates it, however
    many times it is run.

(c) The documented-context fallback is matched against the *start* of a model id.
    A CLI provider's ids are bare (`gpt-5.4`), so they match and resolve to a
    known window. The plain-inference provider's ids are vendor-prefixed
    (`anthropic/claude-opus-5`), so they match nothing and resolve to unknown.

The combined effect is a structural asymmetry, and it runs exactly the wrong way
for independent review: the router treats the tool-enabled route as having known
capacity and the tool-free route as having unknown capacity, so reviewer-shaped
prompts are steered toward the assistant that can read the repository and refused
on the one that cannot.


5. WHY NOTHING WAS CHANGED ON THE ROUTER
----------------------------------------

Setting an operator context window on the plain-inference provider would clear
the gate today, and it was deliberately not done. It is a provider-level value,
so it asserts one context window across every model that provider can reach —
several hundred of them, with real windows ranging from small to very large. That
claim would be false for many, it would apply to the owner's traffic that has
nothing to do with this project, and a wrong value produces silent truncation
rather than a clean refusal. Raising the global unknown-context threshold has the
same character, one level broader.

D016-G authorises a minimal route or profile configuration change. Neither of
these is minimal: both are policy changes to a shared production service, made to
suit one caller. The honest remedies are listed below and they are the owner's to
make.


6. WHAT WOULD CLEAR THIS
------------------------

(a) Carry context_length from the provider's models endpoint into the catalog. It
    is a missing entry in one field whitelist. This is the smallest fix and the
    most correct one: it makes the gate's own evidence tier authenticated rather
    than unknown, using the provider's own declaration.

(b) Canonicalize a vendor-prefixed model id before matching the documented-context
    table, so both provider classes are judged on the same basis.

(c) Bring the local model server up. It is already configured as a plain-inference
    provider; if its catalog exposes context metadata the gate is satisfied
    without any policy change, and the reviewer runs locally at no cost.

Any one of these is sufficient. After it, the formal qualification can run: the
runner is implemented, tested and committed, and it reads the frozen thresholds
rather than restating them.
