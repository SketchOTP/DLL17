1. WHAT D016-F CHANGED, AND WHAT IT DID NOT
-------------------------------------------

D016-F retired three requirements: different commercial providers, different
model families, and proof of which downstream model served a request. Those are
retired in code, not merely in prose — GA-16 no longer blocks on them and
BLOCKED_PROVIDER_CREDENTIALS_UNAVAILABLE and
BLOCKED_AGENTIC_REVIEW_DIVERSITY_UNAVAILABLE are gone from the audit.

D016-F explicitly preserved one requirement, under the heading "Tool isolation":

    Each Paragon request must expose: no web; no search; no functions; no MCP;
    no filesystem; no repository tools; no shell; no connectors.

That is the requirement this record reports on. It is not satisfied, and it is
not satisfiable from the caller's side.

That is the same class of surface D016-D disqualified, reached through a
different door.

4. WHY THIS CANNOT BE FIXED FROM THE CALLER'S SIDE
--------------------------------------------------

PB-4 is the whole finding. `tools: []` and `tool_choice: "none"` are the two
strongest statements the OpenAI protocol lets a caller make about tool use, and
D016-E built the entire formal reviewer path around exactly those two. Both were
sent. Both were ignored, because they were never forwarded: Paragon terminates
the OpenAI protocol at its own boundary and re-issues the prompt into an
assistant whose tool surface was provisioned when that assistant was installed,
not when the request arrived.

So the D016-E proof stops covering the thing it used to cover. For a direct
provider API, what the caller serializes IS the reviewer's tool surface, which is
why ApiReviewerIsolationSelfCheckV1 could settle the question from the request
bytes and settle it in CI. Behind a router, the serialized request and the
reviewer's tool surface are simply two different objects. The request check still
passes — it is asserted for the Paragon backend too, and holds — and it now
proves strictly less than it did.

No client flag fixes this. No jail fixes it either: reviewer_jail.sh confines a
local process, and the tools here execute on the router host, reached over the
network by a component the project does not run.


5. WHY THE FORMAL QUALIFICATION WAS NOT RUN
-------------------------------------------

D016-F says to execute the frozen thresholds "once connectivity and tool-free
request serialization are proven". Connectivity is proven and the request
serialization is proven. The reviewer is not tool-free, and running anyway would
have produced a number that looks like evidence and is not:

  - A reviewer that can read the repository it adjudicates is not reviewing the
    evidence bundle. It can consult the answer. Every metric in
    AgenticReviewerQualificationThresholdsV1 — expected-outcome rate, injection
    resistance, order and position agreement — would be measuring a different
    system than the one the thresholds were frozen for.
  - The first completed formal result is evidence and may not be re-run until it
    passes. Spending that single attempt on a reviewer known in advance to be
    compromised would burn the one clean measurement the programme has.
  - Both slots route to one downstream with one 16k-token preamble, so a
    primary/alternate agreement figure would be close to meaningless.

No scored fixture was shown to any model. The probes asked about shell access and
directory listings; none contained a fixture id, an evidence bundle or the word
VERDICT, and a test asserts that about the recorded probes.


6. WHAT WOULD CLEAR THIS
------------------------

Any one of these, in the owner's gift rather than the coder's:

  (a) A Paragon route that calls a provider's model API directly rather than an
      assistant CLI, so the serialized request is again the whole tool surface.
      The D016-E backends are implemented, tested and unchanged, and the Paragon
      backend would need no change either — only a downstream that forwards
      tool_choice instead of discarding it.
  (b) A downstream assistant profile with tools genuinely removed server-side,
      verified by re-running PB-3 and PB-4 and getting NO_SHELL both times.
  (c) A direct provider credential, which returns the programme to the D016-E
      position where the blocker was one API key.

The probes are cheap and repeatable. If the router changes, re-run PB-3 and PB-4;
if they come back clean, ParagonReviewerBoundary.callerControlsToolSurface()
becomes true on its own, because it is computed from the probe records rather
than written down as a constant.
